# 법령정보지식베이스 제·개정 업데이트 가이드

## 1. 목적과 적용 범위

이 문서는 법령 원문이 제정·개정·폐지되었을 때 `legal_corpus.json`과
법령용어 지식베이스를 안전하게 갱신하는 절차를 정한다. 대상은 현재
저장소가 관리하는 법률·시행령의 조문, 법령용어–일상용어 매핑,
근거 문서 연결, 공식 평가 문항이다.

이 저장소의 `kb_update_manifest.json`은 실제 개정 이력을 주장하는 문서가
아니다. 현재 코퍼스를 기준선과 동일한 후보 데이터로 비교한 무변경
무결성 점검 결과이며, 변경 절차를 재현하기 위한 기준점이다.

## 2. 역할과 책임

| 역할 | 책임 |
|---|---|
| 수집자 | 공식 출처에서 후보 법령 원문과 메타데이터 확보 |
| 주석자 | 변경 조문의 용어·일상어·관계·적용범위 수정안 작성 |
| 검수자 | 원문 대조, 시행일, 관계 유형, 평가 정답의 독립 검토 |
| 승인자 | 전체 검증 결과 확인 후 기준선 교체 승인 |

한 사람이 여러 역할을 수행하더라도 주석 작성과 최종 검수는 서로 다른
단계로 기록한다.

## 3. 업데이트 절차

### 3.1 공식 원문 확보

1. 국가법령정보센터 등 기존 코퍼스와 동일한 공식 출처를 사용한다.
2. 법령 ID, 법령명, 공포일, 시행일, 개정일, 원문 URL을 함께 저장한다.
3. 기준선 파일을 직접 덮어쓰지 않고 후보 코퍼스로 별도 생성한다.
4. 수집 시점과 원문 버전을 기록한다.

### 3.2 변경 탐지

```bash
python tools/analyze_legal_kb_update.py \
  --baseline data/legal_corpus.json \
  --candidate /path/to/candidate_corpus.json \
  --output /tmp/kb_update_manifest.json \
  --mode official_amendment_review
```

도구는 `document_id`를 기준으로 추가·삭제·본문 변경·시점 메타데이터
변경을 구별한다. 공백이나 표현을 임의로 정규화하지 않으므로 공식 원문
변경을 그대로 검토할 수 있다.

### 3.3 영향 분석

변경된 `law_id + article_no` 또는 `source_document_ids`와 연결된 다음
항목을 자동 추적한다.

- 법령용어–일상용어 개념
- 개념의 적용 범위와 주석
- 공식 평가 문항의 기대 법령·조문
- 유효기간과 현행 여부

자동 추적 결과가 없더라도 인접 조문, 위임 조문, 예외 조문에 대한
법률 검토를 생략하지 않는다.

### 3.4 용어 매핑 검수

개정으로 정의나 요건이 달라졌다면 다음을 차례로 확인한다.

1. `legal_term`이 현행 법령 표현과 일치하는가.
2. `lay_terms`가 여전히 같은 개념을 가리키는가.
3. 엄밀한 동의어가 아닌 표현을 `exact_synonym`으로 지정하지 않았는가.
4. `scope_note`가 변경된 요건과 예외를 과도하게 단순화하지 않는가.
5. 폐기된 매핑은 삭제하지 말고 유효기간을 종료하여 이력을 보존할
   필요가 있는가.

### 3.5 유효기간 갱신

- 새 버전의 `effective_from`은 공식 시행일과 일치시킨다.
- 구버전을 보존할 경우 `effective_to`가 새 버전 시작일보다 앞서도록
  관리한다.
- `is_current=true`인 문서에는 `effective_to`를 두지 않는다.
- 공포일과 시행일을 혼동하지 않는다.
- 후보 데이터에 시점 오류가 있으면 도구가 `invalid`로 판정하며 기준선
  교체를 금지한다.

### 3.6 평가 데이터 갱신과 회귀검증

영향받는 평가 문항은 질문의 기준시점, 기대 법령 ID, 기대 조문,
정답 포인트를 다시 검수한다. 그 후 다음을 실행한다.

```bash
python tools/validate_legal_knowledge_base.py
python tools/validate_evaluation_dataset.py
python -m pytest tests/test_legal_kb_update.py -q
python -m pytest -q
```

검색 지표가 변했다면 기존 보고서를 덮어쓰지 않고 새 버전의 평가
보고서를 생성한다.

## 4. 판정 기준

### Pass

- 공식 원문과 본문·시행일·법령 ID가 일치한다.
- 모든 조문과 원문 문서 참조가 존재한다.
- 영향을 받는 용어와 평가 문항의 검수가 완료됐다.
- 전용 검증과 전체 회귀 테스트가 통과한다.

### Revise

- 원문은 확인됐지만 용어 매핑이나 적용 범위에 법률적 판단이 더 필요하다.
- 변경 조문과 연결된 평가 정답이 아직 갱신되지 않았다.
- 관계 유형은 불명확하지만 데이터 자체를 폐기할 정도는 아니다.

### Reject

- 비공식 출처만 존재하거나 원문을 재확인할 수 없다.
- 시행일이 역전되거나 현행·과거 버전이 모순된다.
- 존재하지 않는 법령·조문·문서 ID를 참조한다.
- 일상어를 법률용어와 동일하다고 오인하게 만드는 매핑이다.

## 5. 감사 기록

업데이트 단위마다 후보 코퍼스 해시, 변경 문서, 영향받은 개념·평가 문항,
검수자 판정, 실행 명령과 결과를 남긴다. 실제 변경이 없을 때도
`no_changes` 결과를 기록하여 마지막 확인 시점을 추적할 수 있게 한다.

## 6. 현재 구현의 한계

- 공식 API의 변경 알림을 주기적으로 수집하는 스케줄러는 포함하지 않는다.
- 조문 간 위임·예외 관계의 의미 변화는 자동으로 법률 판단하지 않는다.
- 도구는 영향 후보를 제시하며, 최종 용어 매핑과 정답 변경은 사람이
  공식 원문을 대조해 승인해야 한다.

## 7. 검증된 실제 개정 사례

K4 후보 탐색에서 개인정보 보호법 제15조제1항제7호 신설 사례를
채택했다. 선정 근거, 공식 출처와 예상 영향 범위는
[`K4_AMENDMENT_CASE_RESEARCH.md`](K4_AMENDMENT_CASE_RESEARCH.md)에
기록한다. 현행 검색·답변 데이터에 과거 버전을 섞기 전에 해당 문서의
검증 절차를 먼저 통과해야 한다.

## 8. K5 검수·승인 게이트

K4 분석 결과를 감사 기록으로 승인하기 전에 다음 명령을 실행한다.

```bash
python tools/review_k5_amendment_update.py
```

게이트는 입력 K4 manifest의 SHA-256, 공식 출처, 시행일 일관성, 영향받은
지식 항목·평가 문항의 검수 상태, 단계별 역할 기록과 테스트 증거를
확인한다. 공식 근거나 시점 데이터에 결함이 있으면 `reject`, 검수 또는
회귀검증이 미완료이면 `revise`, 모든 필수 조건을 만족할 때만 `pass`로
판정한다. 사람이 입력한 희망 판정은 게이트 결과를 덮어쓸 수 없다.

현재 포트폴리오 사례는 작성자가 수집·주석·재검수를 서로 다른 단계로
수행한 `staged_self_review`다. 독립된 제3자 검수로 표현하지 않는다.
