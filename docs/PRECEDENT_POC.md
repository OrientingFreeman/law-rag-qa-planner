# 대법원 판례 근거 확장 PoC

## 1. 구현 목적

이번 PoC는 대규모 판례 RAG를 만드는 작업이 아니다. 현재 corpus의 개인정보·노동·전자금융·민사계약 도메인과 직접 연결되는 대법원 판례 10건을 공식 출처로 검증하고, 법령 근거와 판례 근거를 서로 다른 역할과 데이터 유형으로 관리할 수 있는지 확인한다.

법령은 일반적·추상적인 **규범 근거**, 판례는 해당 규범의 의미와 적용 경계를 설명하는 **해석·적용 근거**로 구분한다. 판례가 일반 법령 검색 순위를 바꾸지 않도록 기존 `data/legal_corpus.json`에는 합치지 않았다.

## 2. 구현 범위

- 대법원 판례 10건의 구조화 데이터
- `evidence_type: precedent`를 통한 법령 데이터와의 명시적 분리
- 현재 corpus의 개인정보 보호법·근로기준법·전자금융거래법·민법 조문과 연결
- 판례 해석·구별·시점·잘못된 전제 질문 20개의 평가 데이터
- 공식 출처·필수 필드·관련 조문 존재 여부 자동 검증
- 해석·적용 질문에만 동작하는 보수적 판례 evidence router와 별도 retriever
- API의 `precedent_evidence` 및 웹 화면의 `해석·적용 근거 · 판례` 영역
- 관련도 0.35 이상·공식 출처·사건번호·검증 요약을 모두 갖춘 경우의 결정론적 판례 답변
- 법령 인용 검증과 분리된 판례 근거 검증
- 외부 LLM 생성 프롬프트와 판례 전문 인용 검증 통합은 제외

구현 파일:

- `data/precedent_poc.json`
- `data/precedent_poc.schema.json`
- `evaluation/datasets/precedent_poc_cases.json`
- `tools/validate_precedent_poc.py`
- `tests/test_precedent_poc.py`
- `law_rag/retrieval/precedent.py`
- `tests/test_precedent_retrieval.py`
- `law_rag/generation/precedent_answer.py`

## 3. 데이터 모델

| 필드 | 의미 |
| --- | --- |
| `precedent_id` | 내부 고유 식별자 |
| `evidence_type` | 항상 `precedent`; 법령 근거와 분리 |
| `court` | 법원명 |
| `case_number` | 공식 사건번호 |
| `decision_date` | 선고일 |
| `case_name` | 공식 사건명 |
| `issues` | 판시 쟁점 목록 |
| `holding_summary` | 공식 판결요지를 근거로 작성한 결론 요약 |
| `reasoning_summary` | 공식 판결요지를 근거로 작성한 판단요소 요약 |
| `related_statutes` | 관련 법령 ID·조문·역할 |
| `source_url` | 국가법령정보센터 판례 URL |
| `context_date` | 판례의 해석 맥락 기준일 |
| `legal_context_note` | 구법·현행법 적용상 주의사항 |
| `source_checked_at` | 공식 출처 최종 확인일 |

`holding_summary`와 `reasoning_summary`는 판결문을 창작하거나 비공식 블로그를 재인용한 것이 아니라, 국가법령정보센터가 제공하는 판시사항과 판결요지를 짧게 재서술한 값이다. 원문 확인이 필요한 경우 반드시 `source_url`을 따른다.

## 4. 선정 판례

### 대법원 2017. 4. 7. 선고 2016도13263

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=184700>

개인정보 보호법 제17조의 제3자 제공과 제26조의 처리위탁을 구별하는 법리를 제시한다. 제공받는 자의 독자적 업무·이익을 위한 이전인지, 위탁자 자신의 업무·이익을 위한 이전인지가 핵심이며, 계약의 이름만이 아니라 취득 목적·대가·관리감독·실질적 이용 주체 등을 종합 판단한다.

### 대법원 2016. 8. 17. 선고 2014다235080

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=183259>

이미 공개된 개인정보도 개인정보자기결정권의 보호대상임을 전제로, 객관적으로 인정되는 공개 동의 범위 안에서 처리하는 경우 별도 동의가 필요한지와 위법성 판단 요소를 제시한다. 영리 목적만으로 곧바로 위법하다고 단정하지 않으며, 공개 범위·목적과 후속 처리의 관계 및 충돌하는 이익을 구체적으로 판단한다.

### 대법원 2024. 12. 19. 선고 2020다247190 전원합의체

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=600537>

고정성을 통상임금의 개념적 징표에서 제외하고 소정근로 대가성·정기성·일률성을 중심으로 판단하도록 종전 법리를 변경하였다. 재직조건부 임금과 성과급을 구별하고, 새로운 법리의 원칙적 적용 시점을 2024년 12월 19일 이후로 정했으므로 시점 정보가 필수다.

### 대법원 2015. 5. 14. 선고 2013다69989,69996

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=178075>

구 전자금융거래법 제9조의 사고 범위를 권한 없는 거래, 거래지시 없는 거래, 거래지시와 결과가 불일치한 거래 등으로 해석하였다. 이용자가 직접 지시했고 의도한 대로 실행됐다면 시스템 오류만으로 사고라고 단정할 수 없다. 구법 해석 판례라는 점을 답변에서 밝혀야 한다.

### 대법원 2013. 6. 27. 선고 2013다14880,14897

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=170166>

적법한 이행최고와 기간 경과가 있더라도 기간 안에 이행하지 못한 정당한 사유가 있으면 신의칙상 해제권 행사가 제한될 수 있다고 하였다. 민법 제544조의 형식 요건과 제2조의 신의칙을 함께 평가하는 사례다.

### 대법원 2021. 12. 30. 선고 2021다264673

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=231523>

민법 제536조 제2항의 불안의 항변권은 반대급부를 받지 못할 위험 때문에 선이행 강제가 공평과 신의칙에 반하는 경우인지 양 당사자의 사정을 종합하여 판단한다고 하였다. 계약 당시 예상한 위험이 현실화되었다는 사정만으로 자동 인정되지 않는다.

### 대법원 2025. 7. 18. 선고 2023도3673

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=607821>

소송상 증명이나 방어권 행사를 위해 개인정보 자료를 법원·수사기관에 제출한 경우 정당행위가 될 수 있다고 하면서도, 필요 최소성·비실명화·민감성·침해 정도·대체수단·불가피성 등을 종합하도록 하였다. 개정 전 개인정보 보호법에 관한 판결이라는 시점 표시가 필요하다.

### 대법원 2009. 10. 29. 선고 2009다51417

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=140492>

근로자성은 계약 명칭이나 사업자등록보다 종속적 근로 제공의 실질을 중심으로 판단한다. 기본급·원천징수·사회보험이 없다는 사정만으로 쉽게 부정하지 않고, 지휘·감독과 시간·장소 구속, 독립 사업 위험, 계속성·전속성 등을 종합한다.

### 대법원 2014. 1. 29. 선고 2013다86489

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=172572>

전자금융사고에서 이용자의 중대한 과실은 사고 경위와 범행 수법, 일반인의 인식, 이용자의 직업·금융거래 경험 등을 종합하여 판단한다. 보이스피싱 피해자라는 이유만으로 책임을 자동 인정하거나 부정하지 않는다.

### 대법원 2017. 10. 12. 선고 2016다9643

국가법령정보센터 공식 페이지: <https://www.law.go.kr/LSW/precInfoP.do?precSeq=185875>

계약 당시부터 존재한 원시적 이행불능과 계약 후 발생한 후발적 이행불능의 효과·구제수단을 구별한다. 이행불능은 물리적 불능뿐 아니라 거래관념상 기대할 수 없는 경우와 법률상 금지로 실현할 수 없는 경우도 포함한다.

## 5. 법령과 판례의 역할 분리

| 질문 | 법령 근거 | 판례 근거 |
| --- | --- | --- |
| 개인정보 제3자 제공의 원칙적 요건은? | 개인정보 보호법 제17조 | 통상 불필요; 조문이 직접 규범 근거 |
| 제3자 제공과 처리위탁을 어떤 실질 기준으로 나누는가? | 제17조·제26조 | 2016도13263의 구별 법리 |
| 공개 개인정보는 언제 별도 동의 없이 처리할 수 있는가? | 제15조·제17조 | 2014다235080의 공개 동의 범위 판단 법리 |
| 통상임금에서 고정성이 필수인가? | 근로기준법 제2조·제56조 | 2020다247190의 변경 법리와 적용 시점 |
| 시스템 오류가 모두 전자금융사고인가? | 전자금융거래법 제9조 | 2013다69989,69996의 사고 범위 해석(구법) |
| 최고기간이 지나면 언제나 해제할 수 있는가? | 민법 제2조·제544조 | 2013다14880,14897의 신의칙상 제한 |
| 불안하면 선이행을 거절할 수 있는가? | 민법 제536조 | 2021다264673의 현저한 사유 판단 기준 |
| 재판에 개인정보를 제출하면 언제나 허용되는가? | 개인정보 보호법 제17조·제18조·제59조 | 2023도3673의 정당행위 판단 요소 |
| 개인사업자는 근로자가 아닌가? | 근로기준법 제2조 | 2009다51417의 실질적 종속관계 판단 |
| 보이스피싱 피해자의 중대한 과실은 어떻게 판단하는가? | 전자금융거래법 제9조 | 2013다86489의 구체적 사정 종합 기준 |
| 원시적·후발적 이행불능의 구제수단은 같은가? | 민법 제535조·제537조·제741조 | 2016다9643의 시점별 효과 구별 |

답변에서 법령과 판례를 함께 사용할 때에는 어느 근거가 규칙을 정하고 어느 근거가 해석 기준을 제공하는지 표시해야 한다. 판례 하나의 사실관계를 모든 개인정보 처리에 일반화해서는 안 된다.

## 6. 평가 문항

20개 문항은 다음 실패를 확인한다.

1. 제3자 제공과 처리위탁의 실질적 구별
2. 계약서 제목만으로 처리위탁이라고 단정하는 잘못된 전제
3. 공개 개인정보에는 언제나 별도 동의가 필요하다는 과잉 일반화
4. 영리 목적이면 언제나 위법하다는 과잉 일반화
5. 변경 전 통상임금 법리를 현행 법리로 답하는 시점 오류
6. 재직조건부 임금과 성과급의 판단 기준 혼동
7. 기술적 시스템 오류와 구법 제9조의 법률상 사고 혼동
8. 구법 판례를 현행법 판단으로 무표시 전용
9. 이행최고의 형식 요건만으로 해제 효력을 단정
10. 해제권 제한에 필요한 사실관계 누락
11. 막연한 불안과 불안의 항변권상 현저한 사유 혼동
12. 계약 당시 예상한 위험의 과잉 일반화
13. 재판 제출이면 개인정보 제공이 언제나 허용된다는 과잉 일반화
14. 개인정보 제출의 필요 최소성·비실명화·대체수단 누락
15. 도급계약·사업자등록만으로 근로자성을 부정
16. 기본급·고정급 부재만으로 근로자성을 부정
17. 보이스피싱 중대한 과실의 개별 판단요소 누락
18. 보이스피싱 피해자에게 언제나 책임이 없다는 과잉 일반화
19. 원시적·후발적 이행불능의 효과와 구제수단 혼동
20. 물리적 불능과 법률상 불능의 혼동

평가 데이터는 `expected_precedent_ids`, `expected_case_numbers`, 관련 법령 조문, 최소 답변 포인트를 함께 가진다. 판례 retriever는 이 20문항에서 정답 사건번호 Top-1 20/20을 회귀 테스트로 확인한다. 다만 10개 판례에 맞춰 작성한 소규모 PoC 데이터의 내부 회귀 결과이므로 일반적인 판례 검색 성능이나 외부 데이터 일반화를 의미하지 않는다. 답변 포인트 완결성 평가는 아직 일반 평가 실행기에 연결하지 않았다.

## 7. 검증 방법

```bash
python tools/validate_precedent_poc.py
LAW_RAG_LLM_PROVIDER=deterministic python -m pytest tests/test_precedent_poc.py -q
LAW_RAG_LLM_PROVIDER=deterministic python -m pytest tests/test_precedent_retrieval.py tests/test_api.py -q
```

검증기는 다음을 확인한다.

- 판례가 1~12건 범위인지
- `evidence_type`이 `precedent`인지
- 법원이 대법원인지
- 공식 URL이 국가법령정보센터인지
- 관련 법률 ID·조문이 현재 corpus에 존재하는지
- 평가 문항이 2~24개인지
- 정답 판례 ID·사건번호가 샘플 데이터에 존재하는지

## 8. 한계

- 판례는 10건뿐이므로 검색 성능이나 법률 도메인 전체의 대표성을 주장할 수 없다.
- 판결 당시 법령과 현행 법령 사이의 개정 내용을 완전한 버전 그래프로 연결하지 않았다.
- 판결 전문을 corpus로 수집·분할하지 않았고 판시사항·판결요지 기반 검증 요약만 저장했다.
- 별도 판례 retriever와 evidence routing 및 검증 요약 답변은 구현했지만 법령·판례 교차 ranking, 판결 전문 기반 생성, 외부 LLM이 생성한 판례 인용 검증은 구현하지 않았다.
- 20/20 Top-1은 판례별 검색 별칭을 포함한 폐쇄형 회귀 결과이므로 독립 테스트셋 성능으로 해석할 수 없다.
- 국가법령정보센터 페이지의 변경을 자동 감지하거나 정기 동기화하지 않는다.

## 9. 향후 확장 조건

다음 조건이 충족될 때만 현재의 소규모 분리 검색을 완전한 생성·평가 파이프라인으로 확장한다.

1. 사건번호·선고일·법원·원문 URL을 안정적으로 수집하는 공식 API 또는 동기화 절차
2. 판시사항과 사실관계·방론을 구별하는 annotation guide
3. 법령 버전과 판결 기준시점을 연결하는 temporal model
4. 판례 검색 전용 평가셋과 hard negative
5. 판례 인용 형식과 판시사항 요약을 검증하는 별도 citation validator

현재 구현도 기본 법령 질문은 statute retriever로 처리하고, 해석·적용·판례 요청이 명시된 경우에만 precedent retriever를 호출한다. 다음 확장에서도 이 격리를 유지하여 판례가 일반 법령 검색 순위를 훼손하지 않도록 한다.
